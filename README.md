# Sales Performance Dashboard

Full-stack дашборд аналитики продаж менеджеров: KPI с сравнением к прошлому периоду, динамика, рейтинг менеджеров, категории и товары, последние продажи.

**Стек:** ASP.NET Core (.NET 10) · EF Core 10 + Npgsql · PostgreSQL 17 · React 19 + TypeScript (Vite) · Tailwind v4 + shadcn/ui · TanStack Query · nuqs · Nivo · Motion · Docker Compose.

## Запуск

```bash
git clone <repo> && cd <repo>
docker compose up --build
```

Откройте **http://localhost:8080**. При первом старте backend сам применит миграции и заполнит пустую БД демо-данными (~2 800 продаж за 12 месяцев) — никаких ручных шагов. Повторный старт данные не пересоздаёт; сбросить БД: `docker compose down -v`.

Нужен только Docker (Compose v2). Порты: 8080 (nginx → frontend + прокси `/api`). PostgreSQL и backend наружу не публикуются.

## Архитектура

```
frontend (nginx :80 → host :8080)  ──/api──►  backend (ASP.NET Core :8080)  ──►  postgres
   React SPA, статика                          Controllers + EF Core + raw SQL
```

**Backend** — один проект, папки по фичам (`backend/SalesDashboard.Api`):

| Папка | Что внутри |
|---|---|
| `Domain/` | сущности `Manager, Customer, Category, Product, Sale, SaleItem, Refund, RefundCost`, enum-ы |
| `Data/` | `AppDbContext`, конфигурации, миграции, генератор seed |
| `Common/Periods/` | `PeriodQuery` (валидация) и `PeriodResolver` — единственное место логики периодов |
| `Features/Analytics/` | `AnalyticsQueries` (SQL-агрегаты), `Ledger` (формулы метрик) |
| `Features/Dashboard, Managers, Sales/` | контроллеры блоков дашборда |

Clean Architecture / CQRS / Repository сознательно не используются: задача небольшая, дополнительные слои не решали бы конкретной проблемы.

**Frontend** (`frontend/src`): `api/` — типизированный клиент и хуки TanStack Query; `features/*` — блоки дашборда; фильтры (период, режим рейтинга, шаг графика) хранятся в URL — ссылкой можно поделиться, F5 их не сбрасывает. Каждый блок независимо обрабатывает loading (скелетон), ошибку (сообщение + «Повторить») и пустые данные; при смене периода блок показывает прежние данные приглушённо, а не мигает.

### API

Все эндпоинты принимают период: `?preset=today|7d|30d|thisMonth|lastMonth` **или** `?from=YYYY-MM-DD&to=YYYY-MM-DD` (включительно) + обязательный `tz` — IANA-пояс браузера. Ошибки — `application/problem+json` (400 с описанием полей, 500 с `traceId`).

| Метод | Ответ |
|---|---|
| `GET /api/dashboard/kpi` | выручка, валовая выручка, GP, маржа, продажи, средний чек, доля и сумма возвратов, расходы на возвраты — каждая `{value, previous, change, changeKind}`; лучший менеджер |
| `GET /api/dashboard/timeseries?granularity=auto\|hour\|day\|week\|month` | точки `{bucketStart, revenue, grossProfit, salesCount}`, пустые бакеты — нули |
| `GET /api/managers/ranking?sortBy=grossProfit\|averageCheck` | места, место в прошлом периоде, метрики, изменение метрики |
| `GET /api/dashboard/categories` | выручка, GP, маржа, доля по категориям |
| `GET /api/dashboard/products/top?limit=` | лучшие товары по чистой выручке |
| `GET /api/sales/recent?limit=&cursor=&status=&managerId=` | продажи периода, keyset-пагинация |
| `GET /health` | healthcheck (с проверкой БД) |

## Бизнес-правила

| Правило | Решение |
|---|---|
| **Revenue** | Выручка продаж (Paid + Refunded) **по дате продажи** минус сумма возвратов **по дате возврата** (сторно). Поэтому в коротком периоде выручка может быть отрицательной — это корректно. |
| **Refund** | Возврат всегда полный, хранится отдельной сущностью `Refund` (1:1 к продаже) с датой, флагом `ItemsRestocked` и дополнительными расходами `RefundCost` (логистика, упаковка, экспертиза, прочее). По умолчанию товар возвращается на склад — себестоимость тоже сторнируется; если товар потерян, себестоимость остаётся потерей. |
| **Gross Profit** | `Revenue − (себестоимость проданного − себестоимость возвращённого на склад) − расходы на возвраты`. |
| **Margin** | `GP / Revenue`; при `Revenue ≤ 0` — «нет данных». |
| **Продажи и средний чек** | По дате продажи, Paid + Refunded: `Average Check = валовая выручка / количество продаж` — показывает размер сделок и не «прыгает» от возвратов. |
| **Cancelled** | Не влияет ни на одну денежную метрику и не входит в количество продаж; видна в списке последних продаж. |
| **Предыдущий период** | Отрезок той же длины сразу перед текущим. «Этот месяц» (1–23 сен) сравнивается с 1–23 авг, «прошлый месяц» — с позапрошлым целиком. Изменение денег и количеств — в %, маржи и доли возвратов — в п.п. |
| **Границы дат** | Время хранится в UTC (`timestamptz`); «сегодня», границы дней и бакеты графика считаются в поясе браузера. Интервал полуоткрытый `[from 00:00; to+1 00:00)` — продажа ровно в полночь попадает ровно в один период. Переходы на летнее время обрабатываются. |
| **Лучший менеджер / рейтинг** | Максимум чистого GP. При равенстве: выручка ↓, затем имя — порядок детерминирован. Активные менеджеры без продаж показываются в конце без места; уволенные без активности скрыты. |

## Технические решения

- **Аналитика на raw SQL** (`Database.SqlQuery<T>`): сторно объединяет события по двум датам, а сетка графика строится `generate_series` в поясе пользователя — на LINQ это громоздко и SQL непредсказуем. Параметры передаются как параметры запроса (FormattableString), без конкатенации. Простые выборки (последние продажи, справочники) — EF LINQ с `AsNoTracking` и проекциями; N+1 нет.
- **Одна SQL-агрегация на менеджеров** даёт и KPI (сумма строк), и рейтинг, и лучшего менеджера — метрики гарантированно согласованы. Сумма по графику и по категориям совпадает с KPI (проверено тестами); расходы на возврат распределяются по позициям пропорционально сумме.
- **Деньги** — `numeric(18,2)` / `decimal`; цена и себестоимость фиксируются в `SaleItem` на момент продажи; итоги не денормализуются.
- **Статусы и типы** — C# `enum` ↔ нативные PostgreSQL enum через `MapEnum` (EF 9+). Union types C# 15 рассматривались, но это preview .NET 11 без поддержки в EF.
- **Keyset-пагинация** последних продаж по `(sold_at, id)`: стабильна при вставках и не деградирует на глубоких страницах.
- **Seed** — детерминированный генератор на C# (`Random` с фиксированным seed): профили менеджеров (сильные/слабые, крупный чек, большие скидки, отпуск, новичок, уволенный), сезонность (пик в ноябре–декабре, провал в январе), выходные, ~8 % отмен и ~7 % возвратов (часть — с потерей товара и расходами), несколько крупных сделок-выбросов. Даты отсчитываются от текущего момента, чтобы пресеты не были пустыми.
- **Миграции и seed на старте backend** — ради запуска одной командой (в production — отдельный шаг деплоя).

### Индексы

| Индекс | Зачем |
|---|---|
| `sales (sold_at, id)` | выборка периода и keyset-пагинация (Index Only Scan Backward) |
| `sales (manager_id, sold_at)` | фильтр последних продаж по менеджеру |
| `refunds (refunded_at)` | сторно-агрегаты по дате возврата |
| `refunds (sale_id)` unique | связь 1:1 |
| `sale_items (sale_id)`, `sale_items (product_id)`, `refund_costs (refund_id)`, FK-индексы | join-ы агрегатов |

На seed-данных агрегаты за 30 дней выполняются за ~2 мс (`EXPLAIN ANALYZE`).

## Тесты

- **Backend (47):** юнит — `PeriodResolver` (пресеты, пояса, DST, короткие месяцы), валидация, формулы, генератор seed; интеграционные на реальном PostgreSQL (Testcontainers) — сценарий с вручную посчитанными ожиданиями: сторно в разных периодах, товар на склад/потерян, расходы на возврат, Cancelled, продажа ровно на границах диапазона, разные пояса, рейтинг и tie-break, согласованность графика и категорий с KPI, пагинация без пропусков, 400 на невалидный ввод.
- **Frontend (11):** Vitest + Testing Library + MSW — смена периода (URL и параметры запроса), переключение рейтинга, initial loading, ошибка API с повтором, недоступный сервер, пустой период.
- **E2E (4):** Playwright против поднятого compose.

## Что не успели за 8 часов

- Частичные возвраты (сейчас возврат только полный) и мультивалютность.
- Сравнение менеджеров «лицом к лицу», scatter «выручка × маржа», drill-down из категории в товары.
- Табличное представление графика динамики для скринридеров (сейчас есть подписи и тултипы).
- Генерация TypeScript-типов из OpenAPI вместо ручного `api/types.ts`.
- Seed генерирует продажи в рабочие часы 9:00–20:00 МСК: если стенд поднять ночью, пресет «Сегодня» будет честно пустым.

## Что улучшить для production

- Миграции — отдельным шагом деплоя (efbundle), seed — только для стендов.
- Кэширование агрегатов (HybridCache/Redis) и материализованные дневные агрегаты при росте объёма; партиционирование `sales` по времени.
- Аутентификация и права доступа (видимость по командам), аудит.
- Observability: OpenTelemetry (трейсы SQL, метрики), структурированные логи, алерты по healthcheck.
- CI: сборка, тесты, e2e на compose, проверка миграций; версии образов по digest.
- Секреты подключения к БД — через secret store, а не переменные compose.
